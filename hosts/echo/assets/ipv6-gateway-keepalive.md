# Hyper-V 外部虚拟网络 IPv6 故障排查与技术复盘报告

---

## 第 0 章：基础概念准备

在分析具体故障前，需先明确本次涉及的核心网络概念与通信机制。

### 0.1 外部虚拟交换机与二层桥接
在 Hyper-V 中，外部虚拟交换机（External Switch）的工作原理是将宿主机的物理网卡降级为一个纯二层网桥（Bridge）。
* 宿主机自身被分配一个虚拟网卡，拥有物理网卡的 MAC 地址；
* 虚拟机拥有独立生成的虚拟 MAC 地址（Hyper-V 默认前缀为 `00:15:5d:...`）；
* 在上级网络设备（路由器/交换机）看来，这根网线上挂接了两台完全独立的终端设备。

### 0.2 IPv6 地址分配机制：SLAAC 与临时隐私地址
IPv6 通常不需要 DHCP 服务器，主要依赖无状态地址自动配置（SLAAC，RFC 4862）：
* 路由器定期广播路由器宣告（Router Advertisement, RA），通知局域网当前的公网 IPv6 前缀（例如 `2400:dd01:103a:1012::/64`）；
* 客户端收到前缀后，生成两类地址：
  1. **EUI-64 固定地址**：使用网卡物理 MAC 地址填充后 64 位。由于 MAC 地址全球唯一且固定，该地址永久不变。
  2. **RFC 4941 临时隐私地址（Temporary Address）**：由系统随机生成后 64 位，定期自动轮换。现代操作系统对外建立公网连接时，强制优先使用临时地址以保护用户隐私。

### 0.3 邻居发现协议（NDP）与请求节点组播
IPv6 完全取消了 IPv4 中的全网广播（ARP 广播 `ff:ff:ff:ff:ff:ff`），改用邻居发现协议（Neighbor Discovery Protocol, NDP，RFC 4861）。
当网关要把公网回包转发给局域网的某台主机时，必须先查明该 IPv6 对应的 MAC 地址：
1. 网关向局域网发送**邻居请求报文（Neighbor Solicitation, NS）**，寻址目标为该 IP 对应的**请求节点组播地址**（Solicited-Node Multicast，形如 `ff02::1:ffxx:xxxx`，映射到以太网组播 MAC `33:33:ff:xx:xx:xx`）。
2. 只有监听该组播 MAC 的主机才会处理此请求，并向网关回复**邻居通告报文（Neighbor Advertisement, NA）**。
3. 网关收到 NA 后，把 `(IPv6, MAC)` 写入自身的邻居缓存表（NDP Cache），随后将公网数据包单播推给该 MAC。

### 0.4 网关邻居表的老化机制
网关内存有限，其 NDP 缓存表不会永久保存映射：
* 条目状态通常历经 `REACHABLE`（活跃）$\rightarrow$ `STALE`（陈旧）$\rightarrow$ `DELAY/PROBE`（探测刷新）$\rightarrow$ `FAILED`（失效/删除）；
* 在企业或校园网交换机上，条目老化时间通常在数十秒到数分钟之间。一旦条目失效且重新寻址无应答，网关会直接丢弃该目标 IP 的所有入站流量。

## 第 1 章：故障现象与网络拓扑

### 1.1 网络拓扑
```
上级网关（H3C 交换机，Link-Local: fe80::7625:8aff:fe00:f1ab）
       │
宿舍路由器（全桥接模式，等同于无隔离的二层集线器）
       │
Windows 宿主机（Realtek 2.5GbE 物理网卡，MAC: 00:e2:69:6e:2c:ed）
       │
Hyper-V 外部虚拟交换机（br0）
       │
NixOS 虚拟机（虚拟网卡 eth0，MAC: 00:15:5d:02:65:00）
```

### 1.2 故障现象
1. 宿主机、同宿舍内的 MacBook 以及手机连接同一路由器的 IPv6 均正常，访问外网秒开。
2. 虚拟机能正常通过 SLAAC 获取到前缀为 `2400:dd01:103a:1012::/64` 的公网地址与默认网关。
3. 虚拟机与局域网内其他设备互通完全正常（可与宿主机的 Windows 远程桌面端口 3389、RPC 端口 135 建立双向 IPv6 TCP 握手）。
4. 虚拟机向公网发起访问（例如 `curl -6 http://www.baidu.com` 或 `ping -6 2400:3200::1`）完全超时，丢包率 100%。
5. 每当虚拟机刚重启网卡或添加新 IP 的瞬间，外网能短暂连通 20 到 30 秒，随后必然再次陷入死锁。

## 第 2 章：关键排查路径

排查过程舍弃无关干扰，由以下四个关键节点构成。

### 节点 1：本地系统防火墙与路由规则定界
* 检查 NixOS 内核参数与 iptables/nftables 规则。
* 确认策略路由表 52（Tailscale 路由表）未劫持默认公网路由，内核选路查询确认所有外网目标均指向默认网关 `fe80::7625:8aff:fe00:f1ab`。
* 临时停用系统防火墙并清除反向路径过滤规则（rp_filter），故障依旧。表明丢包不在虚拟机本地出栈过滤链上。

### 节点 2：宿主机驱动级抓包定界（PktMon）
为了确定数据包是否真正离开了物理电脑，在 Windows 宿主机管理员终端运行内核抓包工具 `pktmon` 过滤目标 `2400:3200::1`。抓包结果显示：
* 虚拟机发出的 ICMPv6 Echo Request 经由 `vmswitch.sys` 透传，并被物理网卡驱动 `rt640x64.sys` 记录为 `Tx` 发射到物理网线上。
* 物理网卡上 `Rx`（接收计数）始终为 0。
* **结论**：虚拟机的请求已经物理进入网线，丢包点位于宿主机外部的交换机/网关端，并非 Windows 系统的内部拦截。

### 节点 3：捕捉短暂连通窗口的特征
* 在虚拟机随机新增一个 IP 并立即发起 ping，捕获到了阿里 DNS 的真实单包应答（延迟 11.7ms），但随后第二包起立即丢包。
* 这推翻了“网关物理封锁虚拟机 MAC”的假设，证实网关具备向该虚拟机转发的能力，但依赖某种极易失效的状态条件。

### 节点 4：关键突破，主动注入单播 NS
在连接中断状态下，使用 `ndisc6` 绕过内核常规行为，直接向网关的链路本地地址发送一次定向单播邻居请求：
```bash
ndisc6 -s <虚拟机公网IPv6> fe80::7625:8aff:fe00:f1ab eth0
```
执行后，虚拟机发起的 `curl -6` 访问百度以及 `ping -6` 阿里 DNS 瞬间恢复 100% 连通。

## 第 3 章：根因分析

故障的根本成因是 **Hyper-V 外部交换机配合消费级物理网卡在桥接多 MAC 时的硬件组播过滤缺陷**，具体链条如下：

```
[外网回包到达网关]
       │
[网关需要查明虚拟机 MAC，发出 33:33:ff:... 组播 NS]
       │
[宿主机物理网卡硬件芯片仅监听宿主机自身 MAC 的组播组]
       │
[发给虚拟机的组播 NS 在物理层被直接丢弃，虚拟机从未收到该问询]
       │
[虚拟机未回复 NA] ───> [网关 NDP 邻居表超时置为 FAILED] ───> [网关丢弃回包]
```

1. **组播帧在物理层丢失**：
   公网服务器回包到达上级 H3C 网关后，网关若缓存过期，需通过组播（MAC `33:33:ff:...`）向局域网询问“谁拥有这个虚拟机的 IPv6”。宿主机的 Realtek 物理网卡在全桥接模式下，硬件过滤器未对虚拟网卡的组播组进行全量透传，导致该组播帧在网卡芯片层被丢弃，虚拟机根本收不到网关发来的 NS 问询。
2. **网关侧邻居状态失效**：
   因为虚拟机收不到问询，自然无法向网关应答 NA。网关经过数次尝试无果后，将虚拟机的 NDP 状态标记为 `FAILED`，随后丢弃所有发往该虚拟机的外网回包。
3. **单播保活生效的机理**：
   当虚拟机使用 `ndisc6 -s` 主动向网关发送**单播 NS** 时，数据包直接封装了网关的具体单播 MAC，物理链路通畅无阻。网关在处理该请求时，按 RFC 规范强制提取发送方的源 IP 与源 MAC，并将其状态无条件置为 `REACHABLE`。在此活跃窗口内，网关无需发起任何组播寻址，直接通过单播回包，网络因而完全畅通。

## 第 4 章：最终解决方案与加固设计

为避免手动干预和硬编码，在 NixOS 系统内实现一套自适应的低开销双层保活机制。

### 4.1 核心设计考量
* **零硬编码**：使用 RFC 3849 规定的标准文档测试前缀 `2001:db8::1` 触发本地内核选路查询。系统无论迁移至宿舍、实验室或其它网络环境，均能自动获取当期网关 Link-Local 地址与本机合法的公网临时 IP。
* **防卡死保障**：为 `ndisc6` 配置 `-1 -r 1 -w 250 -q` 参数，设定单次不重试、硬超时 250 毫秒，避免弱网或断网时守护进程挂起。
* **双层状态刷新**：二层单播 NS 确保网关的 MAC 映射持久处于活跃期；三层单包 ICMPv6 报文激活沿途状态防火墙的连接跟踪表项。

### 4.2 配置实现

在对应的 NixOS 主机配置文件（例如 echo 主机配置）中添加以下服务与定时器：

```nix
systemd.services.ipv6-gateway-keepalive = {
  description = "IPv6 dual-layer gateway keepalive";
  wantedBy = [ "multi-user.target" ];
  after = [ "network-online.target" ];
  path = [ pkgs.iproute2 pkgs.ndisc6 pkgs.iputils pkgs.gawk ];
  script = ''
    read -r gw ip < <(ip -6 route get 2001:db8::1 oif eth0 | awk '{for(i=1;i<=NF;i++) {if($i=="via") gw=$(i+1); if($i=="src") ip=$(i+1)}} END {print gw, ip}')
    if [ -n "$gw" ] && [ -n "$ip" ]; then
      ndisc6 -1 -r 1 -w 250 -q -s "$ip" "$gw" eth0 || true
      ping -6 -c 1 -W 1 -I "$ip" "$gw%eth0" >/dev/null 2>&1 || true
    fi
  '';
  serviceConfig = {
    Type = "oneshot";
  };
};

systemd.timers.ipv6-gateway-keepalive = {
  wantedBy = [ "timers.target" ];
  timerConfig = {
    OnBootSec = "10s";
    OnUnitActiveSec = "30s";
  };
};
```

部署并启动后，虚拟机每隔 30 秒自动完成一次毫秒级网关保活，彻底解决了 Hyper-V 外部交换机下的 IPv6 外网断流问题。
